Beneficiary Profile Handoff

The beneficiary detail page names a woman and then tells you nothing about her. This package adds the identity, household and case record, removes the duplicated stage checks, and moves the page to two columns. Everything is built from tokens and classes the app already ships.

Route /wlt/beneficiaries/:id Stack React + TS + Vite, Ant Design API Django REST Design Canvas →

Scope

One route. No change to the registry list, the group pages, or the linkage module.

Out of scope
  • Beneficiary registry list and filters
  • Group detail and linkage pages
  • The edit form itself, beyond deep-linking to a field
  • Amharic translation of the new labels (tracked separately)
In scope
  • New identity header with photo, IDs and five facts
  • Household and case cards
  • Collapsible pathway list replacing two duplicated blocks
  • Two-column layout, money formatting, group logo placeholder
  • 13 new model fields, 2 migrations, one serializer rewrite

Components

Five components. Measurements are the values in the shipped CSS, not approximations.

BeneficiaryIdentityHeader New

Sits directly under the breadcrumb, above every other card. Answers “who is this woman” before the page says anything about programme status.

Container
.card, padding 20px (overrides the default 18px 20px)
Avatar
76×76, --r-group 10px. Photo when present, initials otherwise, dashed “Add photo” button when the record has none and the user may edit. Drops to 60×60 below 780px.
Name
26px / 700 / -0.01em. Deliberately larger than .t-title (22px); it is the page’s subject, not a section heading.
Status chip
.chip. Green “Active”, gold “N details missing”, grey “Exited”. Missing wins over Active when missing_field_count > 0.
Identifier line
13px, --ink-400, tabular figures. Internal ID / PSNP client number / registration date, separated by --closed-border slashes.
Fact grid
5 columns above 899px, 2 below. Age, Phone, Woreda, Kebele, Household size. 14px hairline rule above.
Actions
.btn--sm Edit details, Record contact, then .btn--sm.btn--primary Print profile. Hidden entirely when status is exited. Full-width, 48px tall below 780px.

States

  • Complete — every header field present, green Active chip.
  • Details missing — gold chip counting the nulls; each null cell is a gold Add button that opens the edit form focused on that field.
  • Exited — .card--muted, grey chip, exit date and reason replace the registration date, actions hidden.
  • Read-only user — nulls render an em dash, not an Add button; no action buttons.

Edge cases

  • Name longer than the row: wraps, never truncates. A name is not a candidate for an ellipsis.
  • No date of birth but an estimated age: show the age with the qualifier estimated.
  • One-word name: initials fall back to a single letter.
  • Amharic script names must not clip the 76px avatar; initials use the first grapheme, not the first byte.

API contract

One request fills the page. The response is grouped by card, not flat, so a component maps to a key.

GET /api/wlt/beneficiaries/{id}/
{
  id, 
  identity   { full_name, reference_code, psnp_client_number, photo_url,
               date_of_birth, age, age_is_estimated, phone, woreda, kebele,
               household_size, registered_on, status, exited_on, exit_reason,
               missing_field_count },
  household  { is_head_of_household, marital_status, dependants_count,
               dependants_under_5, disability_type, disability_notes,
               education_level, education_grade },
  case       { development_agent, last_contact_on, enterprise,
               open_grievance_count },
  pathway    { complete_count, total_count, stages[] },
  savings_group { id, name, phase_label, member_count, facilitator_name,
                  joined_on, status, logo_url, meetings_attended, meetings_held },
  finance    { currency, savings_total, loans_received_total, loan_count,
               repayments_total, repayments_principal,
               repayments_service_charge, principal_outstanding },
  linkages   [ { id, type_label, partner_name, active_since, status,
                 blocked_reason } ],
  permissions { can_edit, can_log_contact }
}
Money
Decimal serialised as a string, two places, no locale. The client formats it.
Dates
ISO YYYY-MM-DD. All display formatting is client-side.
Blocked linkage
Same array as active ones, distinguished by a non-null blocked_reason. The client splits them; the server does not send two lists.
Queries
select_related woreda, kebele, development_agent, savings_group; annotate the four derived counts. The current page issues one query per stage check — that must go.
Permissions
Server-side, in the payload. The client must not infer edit rights from a role string.

What to delete

The rework only pays off if the old markup goes with it.

Remove
  • The stage summary block at the top of the page
  • All four REGISTERED / VERIFIED / IN A SAVINGS GROUP / LINKED check cards at the bottom
  • The prose line “Her recorded totals across every savings group she has belonged to”
  • The broken SHG logo image
  • The Female — Yes row from the group checklist
  • The floating admin pill overlapping card content, or reposition it clear of the column
Result
  • Page height drops from roughly 2000px to about 1100px on a laptop
  • Ten checks render once instead of twice
  • Sex moves into identity where it belongs, not into a compliance row
  • Nothing on the page renders alt text as if it were content

Rollout order

This one is a real sequence — each step depends on the one before it.

  1. Migration 0001 — add columns

    All thirteen fields nullable. No backfill, no constraint. Safe to deploy on its own.

  2. Migration 0002 — backfill

    Populate PSNP client number, household size, head-of-household and dependants from the existing import where a value exists. Log rows left null.

  3. Serializer and query

    Grouped response, annotations, permissions. Ship behind the existing endpoint version; the old page keeps working because it reads a subset.

  4. Header, Fact, GroupAvatar

    Land the identity block first. It is the change the field team actually asked for, and it is independent of the pathway rework.

  5. PathwayStageList, and delete the old blocks

    One commit. Landing the new list without removing the old ones ships the page with three copies of the same information.

  6. Two-column layout, money formatting, household and case cards

    Layout last, once the pieces it arranges are stable.

  7. Edit-form deep links

    Wire each Add control to the edit form focused on its field. Until this lands the controls should be hidden, not inert.

Acceptance criteria

Written so a tester can pass or fail each one without asking what was meant.

Identity header

  • A beneficiary with every field populated shows name, green Active chip, internal ID, PSNP client number, registration date, and five facts, all above the fold at 1280×800.
  • A beneficiary with three null header fields shows a gold chip reading “3 details missing”.
  • Every null field renders a gold Add control. No cell is blank and none reads “N/A”.
  • Clicking an Add control opens the edit form with that field focused.
  • A user without change_beneficiary sees em dashes and no action buttons.
  • An exited beneficiary shows a muted card, a grey Exited chip, and the exit date and reason in place of the registration date.
  • A record with no photo shows initials, or an Add photo control for an editor. No broken image, ever.

Pathway

  • The four stage checks appear exactly once on the page.
  • Clicking a row expands its checks and sets aria-expanded="true"; clicking again collapses it.
  • On a partly complete record, the first incomplete stage is open on load.
  • Progress bar width matches the stage ratio, and the row is announced to a screen reader as “N of 4 stages complete”.

Money

  • 1040.00 renders as 1,040.00 ETB with tabular figures.
  • Principal outstanding renders in terracotta with its percentage, and disappears entirely when the balance is zero.
  • No money value is passed through parseFloat anywhere in the render path.

Layout

  • Two columns at 1280px, one column at 899px and below, nothing overlapping at 360px.
  • Page body never scrolls horizontally at any width from 320px to 1920px.
  • Every control is at least 48px tall below 780px.

QA and accessibility

  • Tab order runs breadcrumb → actions → fact Add controls → stage rows → group link → linkages. Focus is visible on every one.
  • Each card is a <section> with aria-labelledby pointing at its own heading.
  • Colour is never the only signal: chips carry text, linkage dots sit beside a written status.
  • Contrast: gold #7a5308 on white passes AA at 14px. Verify the Add link against --surface-alt too.
  • Amharic (lang="am") renders in Noto Sans Ethiopic without clipping in chips, the 76px avatar, or the fact grid.
  • Long values wrap rather than truncate: a 40-character enterprise name, a five-word woreda.
  • Print stylesheet: the profile prints on one A4 page with actions and the rail hidden.
  • Empty states: no savings group, no linkages, zero grievances, all-null household. Each renders a sentence, not an empty card.
  • Slow network: skeletons use the existing .skeleton classes; no layout shift when data lands.

Open questions

Answer these before step 1. Each one changes the schema or the copy.

  1. Does the PSNP import already carry household size, head-of-household and dependants? If so, steps 1 and 2 collapse into one migration.
  2. Is disability captured as a single type or as multiple flags? The enum above assumes one plus a notes field.
  3. Who owns the exit reason vocabulary — free text, or a controlled list? Free text will not aggregate.
  4. Is there a contact log table today, or does “last contact” need one built?
  5. Photo storage and consent: does the consent record already cover holding a photograph?
  6. Should the phone number be visible to every role, or masked for anyone without change_beneficiary?
